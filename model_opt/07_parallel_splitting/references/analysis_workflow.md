# 分析指南

> 从"模型放不下"到"切分方案确认"的完整指南。结构：原理（两个判定）→ 三步分析（每步先讲怎么想、再讲怎么做，估算由脚本完成）→ 通信实现的效率层次 → ★ 方案确认。
---
## 切分的两个判定

一切并行策略都归结为两个判定：

**判定一：在哪里切**——位置只有两级
- 层/模块间：整层或整个模块搬到不同卡，通信只在分界处、频率低 → PP（切层）、EP（切专家）
- 算子内：拆开单个算子的权重/激活，通信穿插执行、频率高 → TP/SP/CP


**判定二：沿哪个维度切**——可切维还是归约维
- **可切维**：算子沿该维不做聚合 → 各卡独立计算、零通信；输出沿该维分片，消费方要完整张量时一次 AllGather 还原
- **归约维**：算子沿该维聚合 → 各卡算出的是部分结果，必须通信完成聚合

【依据】$Y_{ij}=\sum_k X_{ik}W_{kj}$ 对 k 求和，故 GEMM 输入特征维是归约维、输出维是可切维；LayerNorm/softmax 沿特征维求统计量 → 归约维；逐元素操作 → 处处可切。表外新算子按"沿切分维是否聚合"现场推导。

| 策略 | 位置 | 切分维 | 通信 |
|------|------|--------|------|
| PP | 层间 | 层深度 | P2P |
| EP | 模块间 | 分支/专家 | AllToAll |
| TP 列并行 | 算子内 | 权重输出维（可切） | AllGather |
| TP 行并行 | 算子内 | 权重输入维（归约） | AllReduce |
| SP | 算子内 | 激活归约维 | AG+RS |
| CP | 算子内 | 长归约轴 | 环形 P2P |

---
## 拓扑定哪里可切

判定一先看计算图拓扑——结构决定可切位置：

| 拓扑 | 实例 | 切法 |
|------|------|------|
| 链式串行 | Transformer 的 N 层堆叠 | 层间 PP（代价：流水气泡） |
| 独立分支 | 多塔模型 | 各分支分卡 → EP 泛化 |
| 共享主干+路由分支 | MoE | 专家 EP（需评估路由负载均衡） |
| 重复块 | 同构 block 反复堆叠 | 块内 TP/SP、块间 PP |
| 长归约轴 | 超长序列 attention | 沿该轴 → CP |

新架构的分析顺序：查拓扑定可切位置 → 按两个判定定切法 → 查第三步算子表定通信原语（算子级映射以该表为准）。

## 第一步：什么在吃显存？

### 怎么想

显存里的东西按增长方式分三类：

| 状态 | 特征 | 实例 | 切法 |
|------|------|------|------|
| 权重 | 不随输入变化 | 模型参数 | 切权重维（= TP）或按层分布（= PP） |
| 持久状态 | 跨前向步骤保留，随 workload 增长 | KV cache、SSM 隐藏状态、GNN 节点特征表 | 沿增长维切（= CP） |
| 激活 | 单样本前向中间值 | 中间张量 | 沿归约维切（= SP） |

【判据】哪类占主导就切哪类，大小由内存时间线给出。持久状态 = 跨前向保留且沿某维增长；TP/PP 切权重时它同样被切（并行度映射见估算脚本 memory）。

### 怎么做

> 起点：Phase 0 分诊已产出**初步根因组件清单**（组件/大小/缩放规律，见 00_adaptation「OOM 分诊」Step 2）与增长曲线（若跑过 Step 3）——以其为起点补全为完整清单（全组件时间线 + 层内峰值分解 `act_intra`），不重复测算。

读源码，提取：
1. **模型参数**：总参数量、参数显存、框架
2. **模块链路**：每模块输入/输出 shape、主导张量、计算类型、内存复杂度
3. **子模块拆解**：复杂模块列出子模块及各自显存占比

沿 forward 路径构建内存时间线：
1. 逐模块记录中间张量 shape 和生命周期（模块内释放 or 跨模块存活）
2. 计算每模块"同时存活张量总大小"的峰值（串行 N block 峰值 = 单 block 峰值 + 常驻）
3. **递归检查子模块**——隐藏的超线性消费者

产出：三类状态各自的大小与主导项 + **OOM 根因组件清单**——逐个列出导致超限的具体组件（张量/模块名、大小、出现时机、沿哪维增长、可被哪些并行维切分）。根因为单层内瞬态激活（attention score、MLP 中间量等）时，其大小必填 `states.act_intra`（pp 不削减层内峰值，不填会低估 PP 方案显存）。供第二步候选核销、第三步填 spec 的 `states`。

## 第二步：切哪个维度？

### 怎么想

**本步只筛候选，不定案**：按决策树定性选出候选维度（可多个）；通信量比较与并行度取值（满足容量的最小值——通信量随并行度增长）由第三步估算报告定量确认。

【规则】候选必须核销 OOM 根因组件（第一步清单）：根因组件沿其可切维被切、每卡大小降到余量内，候选才有效，否则直接淘汰

维度可切还是归约，按「切分的两个判定」判定二现场判定（沿切分维做不做聚合）。

【启发式】增长阶决定收益：超线性（O(N²)）的维度切它收益最大；线性（O(N×d)）→ 切输入维度。

【启发式】非 2 的幂卡数：优先将 2 的幂部分分配给切权重维度（HCCL 优化好）；序列不整除时 padding 到可整除，计算后裁剪。

持久状态只有 CP（及 TP/PP 的状态绑定）才真正被切分，SP 只切激活。

### 怎么做

定性分类，通过两个问题完成定位：

```
Q1: 显存超限的是什么？
├─ 权重占主导 → 切权重维度（= TP/PP）
├─ 持久状态/激活占主导 → Q2
└─ 两者均超限 → 切权重 + Q2

Q2: 超限的是持久状态还是激活？
├─ 持久状态（跨前向保留）→ 沿状态增长维切（= CP）
├─ 激活超线性维（O(N²)+）→ 沿高阶维度切（= SP；极长归约轴 → CP）
└─ 激活线性维（O(N×d)）→ 沿输入维度切（= SP）
```

产出：**张量分布约定表**——逐张量声明分布方式、每卡 shape、消费操作、恢复通信。须覆盖所有大张量及其配套张量（mask/index/position_ids 等，配套漏切是实测高频错误），未声明张量视为潜在 bug。此阶段为工作产物，在 context 中随估算演进；格式与 evidence_db `parallel_splitting.tensor_distribution_table` 字段一致，★ 方案确认通过后落盘冻结，验证通过后随切分案例入库。

## 第三步：通信代价与可行性

### 怎么想

【规则】切分是三目标权衡：单卡显存 $M$、通信代价 $T_{comm}$、计算效率 $\eta$（流水气泡与未重叠通信拉低）——三者不同时最优，方案比较是显存约束下选通信/效率的帕累托点。

本步目的：运行前完成估算——枚举候选 → 剪掉显存不可行与明显次优的 → 剩余少量候选供实测验证，避免"跑 → OOM → 换切法"的被动试错。

切了归约维，需要通信把部分结果合起来。补什么通信由算子类型决定，不用猜：

| 算子类型 | 切归约维后的通信 | 为什么 |
|---------|---------------|--------|
| 线性（切输入维=行并行） | AllReduce | 各卡算的是部分和，求和还原 |
| 线性（切输出维=列并行） | AllGather | 各卡算的是输出切片，拼接还原 |
| 归约（LayerNorm/softmax） | AG+RS | AG 还原完整输入，RS 分回分片 |
| 拼接（torch.cat/stack） | AllGather | 各卡持有分片，拼接还原完整张量 |
| 拆分（chunk/split） | ReduceScatter | 汇总后分发对应分片 |
| 跨界转置（分片维交换的 permute） | AllToAll | 行切 ↔ 列切的重分布 |
| 分支派发（MoE） | AllToAll | 把数据路由到对应分支 |
| 递归状态（RNN/SSM） | 环形 P2P | 状态在环上传递 |

【规则】通信算子类型由算子语义刚性确定，不能为性能换算子。标准做法列并行+行并行配对，配对时仅一处 AllReduce。

### 怎么做

估算由脚本原地完成。模型与符号的详细说明见脚本注释，文档只规定接口与解读规则：

1. **填 spec.json**：从 [spec_template.json](../scripts/spec_template.json) 复制起步，字段定义（必填/默认/约束）见 [estimate_split.py](../scripts/estimate_split.py) 的 `load_spec` 说明——缺必填、非法值、未知字段均会被脚本报错拦下。核心输入是第一、二步的结论——状态尺寸（读源码提取）与 shape；此外：
   - **regime 来源**：spec 的 dims（b/s 等）取用户显式指定的测试场景（输入文件、shape、batch——用户给定即优先）；未指定时取分诊确认的生产主流 regime
   - **`states.replicated_param_bytes`**：各 rank 复制的参数（LayerNorm 权重、embedding/lm_head 等不被切的部分）。词表大的模型不填会显著低估每卡显存
   - **硬件参数**：典型值，不含各卡时长不齐的同步等待——未校准时通信项可低估约 3 倍。有真实多卡环境时先跑 `comm_self_test.py --timing` 实测等效 α/带宽，填入 `hardware` 覆盖。计算耗时**不是 spec 字段**——脚本按 FLOPs 解析估算（线性项通用；`flops_tflops`/`compute_util` 默认 313T×0.35 可覆盖；架构特有项填 `extra_flops`——attention 模型为 4·L·b·s²·h，其他架构按源码推导）
2. **跑**：`python <skills>/model_opt/07_parallel_splitting/scripts/estimate_split.py --spec spec.json [--cards N]`
3. **读报告**：逐候选的显存分解 vs HBM×0.8、各切分动作的每卡发送量与 α-β 耗时、PP 气泡率、估算延迟与净收益、排序与推荐结论。判断规则（脚本给数据、判断在此）：
   - 候选裁决两级规则：估算延迟差异超出误差带（~30%）→ 延迟定胜负；差异在误差带内 → 方案并列，此时才允许以实现工作量作决胜项
   - 净收益 ≤ 0 的候选剪掉；全部候选 ≤ 0 时仅显存目标可选延迟损失最小者，延迟目标回第二步换维度
   - 根因组件核销：OOM 根因组件在候选下的每卡大小 = 原大小 / 其可切维并行度之积，须有余量。全局峰值达标 ≠ 根因解决。
   - 某方案通信耗时高于其收益 → 回第二步换方案


【边界】脚本不枚举 sp 维（SP 候选直接写进 candidates）、不建模 ep 计算收益（只给通信成本，取决于 MoE 负载均衡）、不覆盖跨维重分布 row↔col（依赖具体模型结构，需要时在报告基础上手工追加）。

### 等价性论证：代数等价 + 数值等价

**代数等价**（方案正确性）：按「切分的两个判定」逐张量推导——被切维度上的算子属于可切维（零通信）还是归约维（按上表配原语），切分 + 通信在代数上与单卡一致。张量分布约定表的"恢复通信"列即由此论证。

**数值等价**（隐性约束）：切分引入两类数值噪声，机制与量级不同：

1. **归约顺序噪声**：浮点加法不满足结合律，切分改变归约顺序（单卡顺序求和 vs 各卡局部求和再聚合），不同方案/并行度结果不同。量级：1e-5（BF16/FP16）~ 1e-7（FP32）。
2. **形状级噪声**（更强，换通信精度不可消除）：切分改变全部 GEMM 输入形状 → kernel tiling 改变 → 舍入序列改变，随深度逐层累积。实测 fp16、48 层模型在极短序列敏感样本上达 1e-2 级；fp32 通信 / fp32 行并行 GEMM 消融均无法消除——固有属性而非实现 bug。

【动作】缩配 fp32 互证（先行分离"逻辑错"与"形状噪声"）：缩小模型配置（减层/减宽、保持同一切分逻辑）+ fp32 跑单卡 vs 多卡，应达 ~1e-7——确认切分逻辑正确。此后全量若超容差，走消融定界 + 例外审批（见 SKILL.md「错误回退」），不在两个层面来回 debug。

是否处理取决于下游用途：

- 一般推理：差异在验证容差内（verify_split.py 分层 tolerance 已覆盖），方案确认时标注预期即可——形状级噪声按 1e-2 级标注，而非仅归约顺序的 1e-5 级
- 评测打分 / RL 一致性 / 科学计算：边界敏感（评测分数可随切权重维并行度漂移）——关键归约点用 FP32 归约（降至 1e-7 以下，代价 2× 归约通信量），或固定归约顺序（跨配置逐位一致，可能无法用最优算法）；仍超容差的形状级噪声按例外审批留痕

## 通信实现的效率层次：先正确，再高效

通信实现分三层优先级，不可混淆——混淆层级会引入正确性 bug 或性能回退：

1. **先对（正确性）**：切归约维后用什么通信算子由算子语义刚性决定（第三步算子表），不能为性能换算子。
2. **再选算法（效率）**：大消息用 Ring（带宽最优），小消息用 Tree（延迟最优），通信库（HCCL/NCCL）按消息大小自动选，不用手动配；判据用于诊断——小消息 KB 级时延迟项 α 主导，减少通信次数比减少通信量更有效。
3. **掩盖优化不在此阶段**：通信与计算的重叠（overlap）属实施/调优阶段。"不做通信优化"仅指此类实施期手段——方案本身的通信代价权衡是分析阶段的核心产出，不可后移。

## ★ 方案确认（分析完成 → 用户确认）

向用户展示并用 `ask_user_question` 确认：

- **切分方案**：张量分布约定表（第二步产出）
- **定量估算**：切分后每卡峰值、通信代价、break-even 结论
- **数学等价性论证**：按第三步「等价性论证」逐张量推导（代数等价 + 数值敏感性判断 + 浮点误差预期标注）
- **风险应对**：known_pitfalls 及 mitigation

展示前自查：
- 切分后每卡峰值 < HBM × 0.8
- OOM 根因组件已核销：第一步清单中的每个根因组件，在选定方案下的每卡大小有余量（沿其可切维的并行度之积折算；全局峰值达标 ≠ 根因解决）
- 每操作通信量 ratio = actual_comm_bytes / lower_bound_comm_bytes ≥ 1.0（< 1.0 = 估算有误；数值取估算报告输出，字段定义见 [schema](../../06_evidence_db/schema.md)）
- 张量分布约定表覆盖所有大张量及配套张量（要求见第二步产出）
- 候选裁决依据完整：估算排序 + 误差带并列判断；工程量仅作并列候选的决胜项
- 每条 known_pitfall 有 mitigation

确认通过 → 张量分布约定表落盘冻结（spec.json 同目录，如 `tensor_distribution.md`），作为实施与验证阶段的契约文件 → 进入实施（[implementation_guide.md](implementation_guide.md)）。evidence_db 记录在验证通过后统一进行（见 implementation_guide「记录与回归」）。
